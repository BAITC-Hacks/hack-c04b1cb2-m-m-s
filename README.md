# ВЭС: прогноз, который можно проверить

Прототип для кейса [«Agentic AI для прогнозирования выработки ВЭС»](https://docs.google.com/document/d/1Fn5IJoj87Fx7IAknG26zkfX8c0eq7feCujd0m66PCgY/edit) трека «Энергетика» HackAlem AI. Пользователь — аналитик ветроэлектростанции, которому нужен 24–48-часовой прогноз с проверяемым происхождением погодных данных. Текущий выход — **нормализованная активная мощность**, не МВт·ч: установленная мощность турбин в ТЗ не дана.

## Реализовано

- Отдельная сглаженная модель «ветер → мощность» для каждой турбины, обученная на исторических 10-минутных измерениях, агрегированных до полных часов.
- Автоматический цикл: архивный запуск ECMWF по координатам обеих турбин → проверка 48 почасовых значений → применение модели → объединение двух прогнозов → анализ диапазона и часовых скачков → сохранение JSON. `watch_forecast.py` самостоятельно проверяет входы по интервалу и повторяет расчёт при изменении погоды или артефакта модели; `--refresh-weather` остаётся разовым ручным обновлением.
- В [results/](results/) сохранены 29 ежедневных прогнозов по 48 часов и [сводный февральский CSV](results/february-hourly.csv) на 672 часа: для каждого часа выбран последний уже доступный прогноз.
- Проверка исходной модели на всём январе и отдельная проверка калибровки ветра на 15–31 января после подбора её параметра на 1–14 января. Результаты и ограничения — [docs/VALIDATION.md](docs/VALIDATION.md).
- Сохранение времени решения, времени запуска погодной модели, калибровки ветра и URL запросов. Кеш позволяет повторить расчёт и пережить повторный старт.

Сверка требований после независимого пробного ревью, выполненные проверки и оставшиеся ограничения — [docs/READINESS.md](docs/READINESS.md).

## Запуск без аккаунтов и исходных CSV

Нужен Python **3.10+**. Для просмотра опубликованных результатов интернет не нужен; для повторного получения погоды он требуется. Внешних Python-пакетов, ключей, подписки, БД и Docker нет. Для локального интерфейса из корня репозитория:

```sh
python3 web.py
```

Откройте `http://127.0.0.1:8000/`. Прогноз на 1 февраля откроется сразу. Для другой даты с 31 января по 28 февраля нажмите «Опубликованный прогноз». На странице — три кривые мощности с календарными отметками UTC, показатели, происхождение прогноза со ссылками на архивные входы и таблица на 48 часов. Ссылка «Скачать весь февраль CSV» отдаёт опубликованный сводный файл на 672 часа. «Пересчитать из архива» повторно получает погодный запуск и показывает новый расчёт, сохраняя его в исключённую из Git папку `predictions/`. При неудачном обновлении уже открытый результат той же даты остаётся на экране с явным сообщением об ошибке. Обычный просмотр и CSV остаются опубликованными снимками; результаты фонового наблюдения доступны отдельно в `predictions/`.

Сервер слушает только локальный адрес. Если порт 8000 занят, выберите другой:

```sh
python3 web.py --port 8001
```

Или `python3 web.py --port 0`: система выберет свободный порт, а сервер напечатает точный адрес.

Для командной строки:

```sh
python3 run_forecast.py 2026-02-01 --model models/power-curve-2026-01-31.json
```

Команда выводит одну строку со средним прогнозом и создаёт `predictions/2026-02-01-forecast.json`. В нём 48 часов, результаты обеих турбин, их среднее и краткий анализ. Артефакт модели включён в репозиторий: он содержит агрегированную кривую и контрольные суммы источников, но не исходные строки CSV. Повтор той же команды использует погодный кеш `weather-cache/`.

## Самостоятельное обновление входов

```sh
python3 watch_forecast.py 2026-02-01 --model-dir models --interval 300
```

После старта процесс каждые 300 секунд заново запрашивает архивный выпуск обеих турбин и перечитывает модель. Изменилось содержимое входов — он сам проверяет данные, пересчитывает мощность и анализ, атомарно сохраняет `predictions/2026-02-01-forecast.json`. При неизменных входах пишет `inputs unchanged`, сохраняя файл и время его изменения. Контрольные суммы входов и результата лежат рядом в `2026-02-01-watch-state.json`, поэтому перезапуск сохраняет это поведение. Ошибка источника не заменяет последний успешный прогноз; следующая проверка повторится по интервалу. Остановка — Ctrl+C.

Это наблюдение за **одной заданной исторической датой**: выпуск погоды остаётся тем же допустимым выпуском, актуальная погода в исторический прогноз не подставляется. Архив обычно неизменен, поэтому отсутствие обновлений нормально. Новую историю измерений процесс не дообучает: он обнаруживает замену уже обученного артефакта модели с допустимым cutoff.

Конечная проверка с реальным API (два цикла и остановка):

```sh
python3 watch_forecast.py 2026-02-01 --model-dir models --interval 5 --max-cycles 2
```

Воспроизводимая проверка самого триггера обновления без сети:

```sh
python3 -m unittest discover -s tests -v
```

Тест имитирует обновление погодного источника, сбой и повреждённые часы, проверяет автоматический перерасчёт, сохранность последнего результата, восстановление и повторный старт. Синтетические входы существуют только во временной папке теста и не попадают в опубликованный февраль.

## Последовательный февральский расчёт

Последовательный расчёт, начиная с 31 января, как требует ТЗ:

```sh
python3 run_forecast.py 2026-01-31 --days 29 --model-dir models
```

Он создаёт 29 ежедневных файлов по 48 часов. Для 31 января используется отдельная модель, обученная до 30 января: будущие измерения 31 января в первый прогноз не попадают. С 1 февраля применяется модель до 31 января. Горизонты соседних дней перекрываются; для каждого файла сохранён свой момент принятия решения.

Опубликованные результаты можно воспроизвести и проверить так:

```sh
python3 run_forecast.py 2026-01-31 --days 29 --model-dir models --output-dir results
python3 export_results.py
```

Первая команда требует интернет при пустом погодном кеше. Для проверки только состава сохранённых JSON и сборки февральского CSV интернет не нужен: запустите вторую команду отдельно. Она проверяет, что 672 часа февраля покрыты без пропусков, и не выбирает прогноз до его времени решения.

## Обучение и январская проверка

Два CSV организатора нужно положить в один локальный каталог под именами `turbine-1.csv` и `turbine-2.csv`. Их оригинальные ссылки находятся в [карточке трека](https://edu.astanahub.com/hackathons/df4743f5-c492-415c-b45a-1f13adb78e06?tab=tracks). По инструкции организаторов исходные данные не включены в репозиторий.

```sh
python3 power_model.py train --input-dir /path/to/csv --cutoff 2026-01-31 --output models/power-curve-2026-01-31.json
python3 power_model.py train --input-dir /path/to/csv --cutoff 2026-01-30 --output models/power-curve-2026-01-30.json
python3 forecast_weather.py 2026-01-01 --days 31
python3 power_model.py train --input-dir /path/to/csv --cutoff 2025-12-31 --output model.json
python3 calibrate_weather.py --model model.json --target-model models/power-curve-2026-01-31.json --input-dir /path/to/csv --output models/power-curve-2026-01-31.json
python3 validate_january.py --model model.json --input-dir /path/to/csv --last 2026-01-31
```

Эти команды повторно строят итоговый артефакт и исходную январскую оценку. Кривая для подбора поправки обучена до января; поправка к прогнозному ветру выбрана на 1–14 января и проверена на 15–31 января по [протоколу](docs/VALIDATION.md). `model.json` и генерируемые результаты исключены из Git.

## Архитектура и источники

`forecast_weather.py` запрашивает Open-Meteo Single Runs API с `models=ecmwf_ifs`, явно задаёт UTC, м/с и конкретный архивный запуск. Для решения 01.02.2026 06:00 UTC используется запуск 31.01.2026 18:00 UTC; этот 12-часовой зазор больше типичной 4–6-часовой задержки публикации глобальных запусков по документации Open-Meteo. `power_model.py` обучает и применяет кривые мощности. `calibrate_weather.py` согласует прогнозный ветер с кривой по ранее доступным данным. `run_forecast.py` управляет последовательностью, проверяет результат, выявляет часы низкой мощности и резкие изменения, затем сохраняет JSON. `validate_january.py` считает предварительные ошибки.

Подробная схема автономного цикла — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Источники, модели, данные и условия использования — [docs/SOURCES.md](docs/SOURCES.md). Пошаговая демонстрация и часовые результаты — [WALKTHROUGH.md](WALKTHROUGH.md); подробный журнал — [docs/PROGRESS.md](docs/PROGRESS.md). Для отдельной формы организатора подготовлен [черновик подачи](docs/SUBMISSION-DRAFT.md); сама форма ещё не отправлена. Всё, кроме Python 3 и внешнего HTTP API погоды, работает локально. Секреты не используются.

## Проверка ошибок и ограничений

```sh
python3 forecast_weather.py bad-date
python3 run_forecast.py 2026-02-01 --days 0 --model models/power-curve-2026-01-31.json
```

Обе команды должны завершиться с ошибкой. При неполном погодном ответе расчёт останавливается; некорректные единицы ветра и разрывы часов отклоняются. Неизвестны часовой пояс меток CSV, высота измерения ветра датчиком и веса турбин по установленной мощности. Поэтому объединение — арифметическое среднее двух нормализованных выходов при допущении равной мощности. Калибровка уменьшила январскую ошибку, но [цифры проверки](docs/VALIDATION.md) нельзя считать февральской точностью. Фактических февральских значений в предоставленных CSV нет.

Проверено 23.09.2026: архивы для обеих турбин на 31.01–28.02 без пропусков; последовательный расчёт создал 29 файлов, 1 392 почасовые строки с перекрытием горизонтов. Из свежего клона официального репозитория без исходных CSV и погодного кеша локальный сервер открыл сохранённый прогноз на 28.02 (48 часов), а сборка CSV дала побайтно тот же результат, что хранится в Git. Повторный расчёт 01.02 через погодный API также дал те же 48 значений, что и опубликованный JSON.
